# Asset conventions: Blender to Unreal Engine 5.8

These are the rules the validator (`dinkasset/validate.py`) enforces and the exporter
(`dinkasset/export_ue.py`) assumes. The machine-readable copy is
`dinkasset/conventions.py`; the class table below is generated from it and
`run_tests.py` fails if the two drift apart.

Every rule has its reason, so an exception can be argued instead of guessed at.

**Evidence labels used in this document**

| Label | Meaning |
|---|---|
| *(tested)* | Checked on this machine with Blender 5.2.2 by `run_tests.py`: either in Blender, or by reading the exported FBX/GLB bytes with a stdlib parser. |
| *(docs)* | Taken from Unreal or Blender documentation or experience; Unreal is **not installed** here, so nothing was import-tested in the editor. |
| **verify in editor** | Unreal 5.8 behaviour I am not certain of. Check it with the first real import and write the result into `AGENTS.md`. The consolidated list is in section 14. |

Numbers marked *(starting value)* are first guesses to be re-based on the Steam Deck
test scene that the plan makes a pre-production gate (`REMASTER_PLAN.md` section 10).

## 1. What an asset is

**One asset = one collection** in a `.blend`, named exactly like the Unreal asset
(`SM_Barrel_01`). The collection carries custom properties; the scripts only look at
collections named `SM_*`/`SK_*` or carrying `dink_class`.

| Collection property | Meaning |
|---|---|
| `dink_class` | **Required.** One of the classes below. Everything (pivot, budget, LODs, collision) follows from it. |
| `dink_path` | Optional sub-folder under the class folder, e.g. `Tavern` gives `/Game/Dink/Props/Tavern/SM_Barrel_01`. |
| `dink_nanite` | Optional `yes`/`no`, overrides the class policy. |
| `dink_tex_px` | Optional. The texture edge you actually use, so the texel-density check can judge the UV layout. |
| `dink_translucent` | `1` for translucent materials: forces Nanite off and demands a LOD chain. |
| `dink_source` | Free text for the asset ledger (generator, model, licence, prompt id). |

Objects inside the collection:

| Object | Name | Count |
|---|---|---|
| Render mesh | `<Asset>` (no LODs) or `<Asset>_LOD0`, `_LOD1`, ... | exactly **one mesh object per LOD** (join parts; Unreal merges separate objects unpredictably) |
| Collision | `UCX_<LOD0 mesh name>_NN` (`_01`, `_02`, ...) | 0..n convex hulls |
| Armature (skeletal only) | any name, convention `<Asset>_Armature` | exactly 1 |
| Socket | Empty named `SOCKET_<Name>` | 0..n (weapons need `SOCKET_Grip`) |

Nothing else is exported (a reference image, camera or light in the collection earns a warning).
The asset may sit anywhere in the scene (to lay assets out side by side): the exporter
moves it to the origin for export and moves it back.

## 2. Units, axes, scale

**Rules**

1. Blender scene units: **Metric, Unit Scale 1.0**. One Blender unit is one metre. The
   validator rejects anything else (`SCENE_UNITS`); `fix.py --fix-units` converts and keeps real sizes.
2. Model at real-world size. Dink is about 1.7 m; a 2 m grid cell is a 2 m cell.
3. Rotation and scale are always **applied** (1,1,1 / 0,0,0). Location is free in the `.blend`.
   Negative scale is an error (it flips winding and breaks normals).
4. **Z is up. The asset's front faces -Y** (the direction Blender's numpad-1 front view looks at).
   Left/right is the asset's own left/right.

**Why metres.** Blender's tools, physics, lights and bevel widths assume metres; the
plan's real-world sizing (2 m kit, 3.5 m ceilings) is stated in metres. Unreal works in centimetres.
The conversion happens once, in the exporter, so nobody ever types "100" into a field.

**What the exporter writes** *(tested: header and vertex data read back from the file)*

| Setting | Value | Why |
|---|---|---|
| FBX version | Blender 5.2 default (binary 7.4) | what the exporter produces; Unreal reads 7.x |
| `apply_unit_scale` / `global_scale` | `True` / `1.0` | unit scale 1.0 so nothing else to compensate |
| `apply_scale_options` | `FBX_SCALE_ALL` ("FBX All") | writes `UnitScaleFactor = 100` (the file says "my unit is 100 cm") and leaves **every node scale at 1.0**. The default `FBX_SCALE_NONE` instead puts scale 100 on each object and bone, which is the known source of 100x armature/bone trouble. |
| `axis_forward` / `axis_up` | `Y` / `Z` | identity for Blender: **no rotation is baked** into any node, header declares Z-up, front axis -Y (FBX "Maya Z-up", the same system Unreal converts to) |
| `bake_space_transform` | `False` | nothing to bake, so no rotated/scaled nodes |
| `use_triangles` | `True` | triangulate **on export only**; the source keeps quads for editing |
| `mesh_smooth_type` | `FACE` | writes smoothing groups; Unreal warns when a mesh has none |
| `use_tspace` | `False` | tangents are computed by Unreal (MikkTSpace); do not export Blender's |
| `add_leaf_bones` | `False` | otherwise every bone chain gets a junk `_end` bone |
| `bake_anim` | `False` | this iteration exports mesh + skeleton only, no animation |
| `path_mode` | `STRIP` | textures are imported from the `Textures/` folder next to the FBX, not by absolute path |
| `object_types` | mesh, armature, empty | sockets are Empties |
| Placement | asset moved to the origin during export | the pivot becomes the mesh origin |

`--fbx-scale-mode local|units` on `export_ue.py` selects the other Blender modes if the first
editor import shows a 100x or 0.01x size error. The manifest records the mode used.

**What Unreal should do with it** *(docs; **verify in editor**)*:

* Unreal converts an FBX scene to centimetres from the unit header, so a 0.9 m barrel arrives
  as 90 uu tall. Import with *Import Uniform Scale = 1.0* and *Convert Scene* on.
  Expected size is in the manifest (`bounds_cm.size_cm`); the first import must match it.
* Unreal mirrors Y when converting from the right-handed FBX space to its left-handed space.
  Our file is Z-up with the front on -Y, so the asset's front lands on **+Y in Unreal asset space**
  (`bounds_cm.unreal_min_cm/unreal_max_cm` in the manifest are already in that space).
  This is also how the UE5 Manny/Quinn meshes sit (their front is +Y; the character
  blueprint rotates the mesh component by -90 degrees yaw). Do **not** tick "Force Front X Axis".
  If the first import shows the front on +X, change the exporter's `axis_forward` rather than rotating assets by hand.
* Placement code (the future `DinkImport`) must therefore treat **+Y as the front of every imported mesh**.

**glTF/GLB** *(tested: accessor bounds read from the .glb)*: metres, Y-up, +Z forward (glTF spec),
which is Blender (x, y, z) -> glTF (x, z, -y); the Blender front (-Y) is glTF +Z.
The `.glb` contains LOD0 (and the skin) only: no collision, no LOD chain. It exists for
previews, other tools, and Unreal's Interchange glTF pipeline; **FBX is the Unreal path**
because `UCX_` collision, LOD naming, sockets and skeletons are FBX conventions.
How Unreal's glTF importer maps axes and scale: **verify in editor**.

**Round trip** *(tested)*: re-importing the exported FBX and GLB into Blender gives the
same size to within 0.5 cm and the front marker on -Y again; the test also reads the FBX
header, node transforms and vertex extents without Blender's importer.

## 3. Pivot (origin) by class

The origin is the placement point in Unreal, so it has to be somewhere a level designer
(or the importer script) can predict.

| Rule | Classes | Origin | Reason |
|---|---|---|---|
| `base_center` | props, foliage, buildings | centre of the bounding box in X/Y, bottom of the mesh in Z. X/Y tolerance is 10 % of the extent (a protruding tap or handle must not force a lopsided pivot); Z tolerance 1 cm. | Drops onto the floor, rotates about its own vertical axis. |
| `grid_wall` | `kit_wall` | left end of the wall (bounds min X = 0), **centre line of the wall thickness on y = 0**, floor level (min Z = 0). The wall runs along +X. | Two walls meeting at a grid vertex share the centre line, so corners and T-junctions line up without offsets. Rotating by 90 degrees about Z keeps the wall on the grid. |
| `grid_floor` | `kit_floor` | min X = min Y = 0 corner, **top surface at z = 0**. The tile extends into +X, +Y and down. | The floor top is the walking level and the wall base level, so tiles and walls need no vertical offset. |
| `grid_ceiling` | `kit_ceiling` | min X = min Y = 0 corner, **underside at z = 0**; place at z = 3.5 m. | The visible surface is the reference. |
| `grid_piece` | `kit_piece` | at floor level (min Z = 0) and inside the footprint; model it so the origin is a grid vertex (the validator cannot check the grid position, only floor level and footprint; `fix.py --set-pivot` snaps to the 0.5 m vertex nearest the bounds centre). | Pillars, corners, stairs, arches. |
| `hinge` | `door` | on the hinge edge (min X = 0), centred through the thickness, at floor level. Closed leaf extends along +X. | Opening a door is a rotation about the origin: no pivot offset in Blueprint or animation. |
| `grip` | `weapon` | at the grip; `SOCKET_Grip` Empty sits on the origin. | Attaches to the hand socket without an offset. |
| `feet` | characters, creatures | at floor level between the feet; the **armature object origin** is the reference, mesh bounds are measured from it. Tolerance in X/Y: 15 cm humanoids, 50 cm creatures. | Capsule and root motion expect feet on the ground at the root. |

Tolerance for exact rules is 1 cm (`SNAP_TOL_M`). `fix.py --set-pivot` applies the same
rule (not for rigs: move those by hand).

## 4. Modular grid

Plan: one 2 m interior kit, 3.5 m ceilings.

* **Horizontal grid 2 m**, allowed sub-module 0.5 m. A wall/floor/ceiling extent that is not a
  multiple of 0.5 m is an error (`SNAP`); a multiple of 0.5 but not 2 m gets an *info* ("half module").
* **Vertical: storey height 3.5 m** from floor top (z = 0) to ceiling underside. Wall height must
  be a multiple of 0.5 m and at most 3.5 m (`kit_wall`).
  Sub-grid 0.5 m divides both 2 m and 3.5 m.
* **Wall thickness 0.2 m** is the kit default *(starting value)*. Keep walls and floors
  **thick, closed solids** (10 cm or more): Lumen leaks light through thin shells **(verify in editor)**,
  and closed solids give cleaner Nanite and distance fields.
* Door openings: 1.0 m wide x 2.2 m high on the 0.5 m grid *(starting value)*; the
  test module `SM_Wall_Door_2m_01` is the reference.
* **Exterior kits** (13 building families in the plan) follow the same rules on a
  **4 m horizontal grid** with the same 0.5 m sub-grid. This is my proposal, not in the plan; tune it in the greybox.
* Everything snaps in Blender with Increment Snap = 0.5 m (0.25 m for trim) and Vertex snap for mating faces.

## 5. Naming

Unreal names are case-sensitive in tooling and impossible to rename cheaply once referenced.
Prefix rules follow the usual Unreal community style so the asset type is visible in every list.

| Thing | Pattern | Example |
|---|---|---|
| Static mesh asset | `SM_<Name>` | `SM_Barrel_01`, `SM_Wall_Door_2m_01` |
| Skeletal mesh | `SK_<Name>` | `SK_Dink`, `SK_Goblin_Archer` |
| Texture | `T_<Material without MI_>_<suffix>`, suffix = `BC N ORM E MSK H` | `T_Barrel_Wood_BC` |
| Material instance | `MI_<Name>` | `MI_Barrel_Wood`, `MI_Stone_Trim_01` |
| Master material | `M_<Name>` | `M_Standard`, `M_Foliage` |
| LOD mesh object | `<Asset>_LOD<n>` | `SM_Tree_Oak_01_LOD2` |
| Convex collision | `UCX_<LOD0 mesh name>_<NN>` | `UCX_SM_Barrel_01_01` |
| Socket | `SOCKET_<Name>` | `SOCKET_Grip` |
| Bone | lower-case, `_l`/`_r`, **no** `.L`/`.R`, spaces or dots | `upperarm_l` |

Rules: ASCII, `PascalCase` tokens separated by `_`, each token starts with a capital or digit,
**no `.001` suffixes** (Blender adds them on duplicates; they are the first sign of a messy file),
at most 48 characters, two-digit variant numbers (`_01`). Tokens carry meaning, e.g. `_2m` for the module length.
`UBX_`, `USP_`, `UCP_` (box, sphere, capsule) are legal in Unreal but not produced here; the validator warns.

Notes:

* **UCX naming and LODs**: collision is named after the **LOD0 render object**
  (`UCX_SM_Tree_01_LOD0_01` when a chain exists). I believe Unreal matches collision by that node
  name; whether it strips the `_LOD0` token is **verify in editor** (Interchange and the legacy FBX
  importer may differ). `make_lods.py` and `fix.py --rename` keep the names consistent when LOD0 is renamed.
* **LOD naming**: Unreal builds a LOD chain from one FBX containing `<Name>_LOD0`, `_LOD1`... mesh nodes *(docs; **verify in editor**)*.
  A mesh with no chain is named `<Asset>` (no suffix).
* Materials in Blender are *placeholders for Unreal material instances*. The Blender material name becomes the
  Unreal material slot name; the future import script replaces it with the `MI_` asset of the same name.
  Optional property `dink_master` on the material records the master it should parent to (`M_Standard` default); not validated yet.
* Animation assets (`A_`, blendspaces, montages) are not covered: this iteration exports no animation.

## 6. Budgets and texel density

Target: third-person camera behind Dink on mid-range PCs and the Steam Deck (plan section 2).

**Triangles** (table in section 1) are budgets for **LOD0 per asset**:

* Props and kits are mostly Nanite, where raw triangle count matters less than **authoring time, disk and
  streaming size**, and the 1997 look wants clean silhouettes, not scans. Budgets are therefore set where an
  AI-generated mesh (often 100k-1M triangles) must be *reduced and cleaned*, not left raw.
* Skeletal meshes are **not** Nanite *(starting policy, see section 9)*, so they pay per-vertex skinning cost
  on every character on screen; the budgets are tight enough for roughly ten characters at LOD0/LOD1 on the Deck.
  Hero 40k/70k, NPC and goblin 20k/35k, quadruped 15k/30k *(starting values)*.
* Over target = warning, over hard max = error. `import_generated.py` collapses an over-max generated mesh to the target.

**Texel density** *(starting values)*. Screen pixels per metre at distance d are
`H / (2 d tan(fov_v / 2))`. At 1080 p with a 90 degree horizontal FOV (about 58.7 degrees vertical):
320 px/m at 3 m (normal camera), 640 px/m at 1.5 m (conversation close-up). On the Deck TSR renders
below native resolution, so about half of that is visible. Hence:

| Use | Target px/m | Why |
|---|---|---|
| Props, kits, doors | 512 | matches the close-up camera; seen from 3 m it is already oversampled 1.6x, which TSR needs |
| Large props, buildings | 256 | seen from a distance or in pieces |
| Characters, creatures, held items | 1024 (hero body) / 512 creatures | close-ups happen on faces and hands |
| Terrain/ground tiling materials | outside this toolchain | tiling PBR sets: 1024 px per 2 m, set in the Unreal material |

The validator checks density only for unique-UV classes: it computes the texture edge needed to
hit the target from the UV layout, and warns when that exceeds the class cap; if `dink_tex_px` is
set it checks the density at that size (accepted band 0.5x-2x of target).
Trim-sheet kit classes are exempt.

## 7. Materials and textures

* **Material slots** per mesh: see the class table (kit 2, prop 3, hero 6). Every slot is a draw call
  per mesh and a separate Nanite material bin; characters need a few (skin, cloth, hair, eyes), props do not.
  Slots must be used (an unused slot is a warning) and filled (an empty slot is an error).
  `fix.py --prune-slots` removes unused slots and merges `.001` duplicates.
* **Shared trim sheets** carry kit pieces (UV overlap allowed, `uv_overlap = true`); **unique bakes** carry props
  and characters (UV islands must not overlap, `UV_OVERLAP`). Mirrored UVs on a unique-texture prop break
  baked AO and normals, which is why overlap is forbidden there.
* **Texture set** (all power-of-two edge, every mip level from 4 px; not larger than the class cap):

  | Suffix | Channels | Colour space | Unreal compression *(docs; verify in editor)* |
  |---|---|---|---|
  | `BC` | RGB base colour (+A opacity only for masked/translucent) | sRGB | Default (BC1/BC7) |
  | `N` | tangent-space normal | linear | Normalmap (BC5) |
  | `ORM` | R = ambient occlusion, G = roughness, B = metallic | linear | Masks (no sRGB) |
  | `E` | emissive | sRGB | Default |
  | `MSK` | single-channel mask | linear | Grayscale/Masks |
  | `H` | height (parallax or displacement) | linear | Grayscale |

  Packing ORM is how Unreal's own materials expect it (one texture fetch for three channels);
  glTF's metallic-roughness image (G, B) is close to it, which `import_generated.py` takes advantage of when it names images.
* **Normal map green channel.** Blender bakes OpenGL-style (Y+) normals; Unreal expects DirectX-style (Y-).
  Either bake with Y- or tick *Flip Green Channel* on import. The manifest marks normal textures
  `normal_green_flip: true`. **verify in editor** on the first textured import.
* Textures are not baked or packed by these scripts: they are exported (copied or saved as PNG) into `Textures/` next to the asset.
  A packing script (Pillow is available on the host) is future work.
* Vertex colours are not exported (`colors_type = NONE`); add a deliberate path when foliage wind or paint masks need them.

## 8. UV channels

| Channel | Use |
|---|---|
| UV0 | **Required.** The texture set (unique unwrap or trim-sheet placement). Triangle UVs outside 0-1 are a warning on unique classes. |
| UV1 | **Optional.** Only for a second mapping the material really needs (macro variation, decals, a second texture set). At most 2 UV maps; more earns a warning because each costs vertex memory. |
| Lightmap UVs | **Not needed.** The remaster uses Lumen: it traces the scene and caches lighting on mesh cards, so there is no baked lightmap and no lightmap UV channel. Nanite meshes cannot use baked lightmaps at all. Leave *Generate Lightmap UVs* **off** on import (the manifest says so). If baked lighting is ever added for a low-end mode, generate lightmap UVs in the editor for the affected assets then. |

## 9. LOD policy and Nanite

Plan: Nanite, Lumen, Virtual Shadow Maps, TSR.

| Class group | Nanite | LOD chain | Why |
|---|---|---|---|
| props, large props, buildings, kit pieces, doors | **yes** | not required | opaque rigid meshes are Nanite's strength; thousands of kit pieces |
| `prop_small`, `weapon` | **no** | optional (0.5, 0.25) | tiny low-poly meshes cost more in Nanite than they save *(verify in editor; measure on the Deck scene)* |
| `foliage` | **no** *(decision pending)* | **required**: at least 3 levels (LOD0-LOD2); `make_lods.py` builds LOD1-LOD3 at 0.5, 0.25, 0.1 | masked, two-sided leaf cards overdraw badly in Nanite; Unreal's Nanite foliage support has been maturing since 5.x and may be production-ready in 5.8: **verify in editor** and flip the class to `yes` with `dink_nanite` or the table if it holds on the Deck |
| translucent (`dink_translucent = 1`) | **no** (Nanite does not render translucency) | **required**, min 3 levels | |
| skeletal meshes (characters, creatures) | **no** | **required**, 4 levels hero/NPC, 3 creatures; ratios 1, 0.5, 0.25, 0.12 | Nanite skeletal meshes are new and restricted in 5.x; classic LODs are the safe baseline for ~60 NPCs on the Deck. **verify in editor** whether 5.8 makes Nanite skeletal worthwhile |

LOD generation (`make_lods.py`): LOD n is the Decimate-collapse of **LOD0** (not cascaded), triangulated, delimited by material,
at the class ratios, never below 24 triangles. Each LOD must be at least 2 % lighter than the previous one and the
bounds must stay within 10 % of LOD0 (`LOD_BOUNDS` warning catches decimation that shrinks thin parts).
For skinned meshes the decimation runs on the rest-pose mesh and the Armature modifier is re-attached; vertex weights
survive *(tested on the skinned test tube)*. Automatic decimation is a **starting point**: hero characters and anything with faces/hands need hand-made LODs.

LOD screen sizes (Unreal side) *(starting value)*: LOD0 1.0, LOD1 0.4, LOD2 0.15, LOD3 0.05, tuned on the Deck test scene.
A Nanite class that nevertheless has a LOD chain gets an *info* (the chain is only the fallback mesh).

## 10. Collision

* Classes with `collision = required` need `UCX_` hulls (props that characters collide with, every kit piece, doors, buildings).
  `prop_small`, `weapon`, `foliage` are optional. Characters/creatures use a capsule and a Physics Asset in Unreal, not UCX.
* Unreal only treats **convex** hulls as simple collision. The validator tests that every hull is a closed, convex solid, at most 32 vertices
  (warning above, hard error above 255). It does not require manual hulls to be minimal.
* `make_lods.py --collision`:
  * `hull` (default for props): one hull of the whole mesh. A barrel hull is about 27 vertices.
  * `grid` (default for kit pieces and buildings): the mesh is clipped into 0.25 m cells (0.5 m for buildings), occupied cells are merged
    into boxes, and each box gets one hull of the geometry inside it. Door openings and arches stay open *(tested: points in the door opening
    are outside every hull, the lintel and both columns are inside)*. Walls become 3 hulls instead of a solid slab.
  * `box`: one axis-aligned box.
  * Concave props (stairs, arches) deserve hand-made hulls; the generated ones are a floor, not a ceiling.
* The collision objects live in the asset collection, share the pivot, are drawn as wire and are hidden from render.
* Unreal import: *Auto Generate Collision* **off**, *Use custom collision from file (UCX)* on. Whether `UCX_` import survives the move to Interchange
  as the default FBX path in 5.8 is **verify in editor**.

## 11. Skeleton policy

The plan: one UE-mannequin-compatible humanoid skeleton shared by Dink, NPCs and goblins; one quadruped skeleton (pig, bonca).

* **Humanoid (`SK_Dink_Humanoid`, class `character_hero` / `character_humanoid`).** Bone names and hierarchy follow the UE5 Manny/Quinn
  skeleton so Epic's animation content, the IK Retargeter and motion matching samples work with trivial chain mapping.
  The validator requires the core set: `root, pelvis, spine_01..spine_05, neck_01, neck_02, head`, and per side
  `clavicle, upperarm, lowerarm, hand, thigh, calf, foot, ball`, with `_l`/`_r`. Fingers, twist, IK (`ik_foot_root` ...) and
  `interaction`/`center_of_mass` bones are optional now and should be added when the first character is rigged. **That list is from my memory of the UE5 mannequin: verify in
  editor against the real Manny before the first rig is built.**
* **One Unreal Skeleton asset.** The first humanoid import creates `SK_Dink_Humanoid`; every later humanoid mesh (NPCs, goblins, child) is imported
  *against it*. Meshes with different proportions (the child, the goblins) keep the same bone names and hierarchy; Unreal's
  per-bone retargeting modes (Animation, Skeleton, Animation Scaled) let the shared animations adapt **(verify in editor; if proportions differ a lot, retarget with an IK Rig instead)**.
* **Quadruped (`SK_Dink_Quadruped`, class `creature_quadruped`).** Unreal has no standard; the project definition is in `conventions.py` (`QUADRUPED_BONES`):
  root, pelvis, three spine, two neck, head, three tail bones, and per side front `upperarm/lowerarm/hand` and rear `thigh/calf/foot`.
  Freeze this list when the pig is rigged.
* **Bespoke creatures (dragon, pillbug, duck, stone giant)**: any skeleton with a single root bone named `root`.
* Rules for every skeleton: one armature, single root bone `root` at the asset origin, **deform bones only** (no control or helper bones in the exported armature;
  keep the animator's control rig in a separate collection that is not part of the asset), no `.L/.R` names, each vertex weighted to at least one bone,
  at most **4 influences preferred (warning above 4), 8 hard limit**. Unreal's default is 4; the project setting for more
  is **verify in editor**. Armature transforms are applied; the armature object origin is the pivot.
* **Bone axes.** Blender writes bone orientation into the FBX (Y along the bone: `primary_bone_axis=Y`, `secondary=X`). Manny's local axes differ. That is fine for animation
  retargeting (chain based) but means Manny animation assets do not play directly on our skeleton without the retargeter. *(tested: bone
  positions survive the round trip to 0.5 cm)*
* **Armature node.** Blender exports the armature object as a Null parent of `root` (tested: it appears in the FBX). Unreal normally ignores it for skinned
  meshes, but a stray extra root bone named after the armature object has been reported. **verify in editor**; if it happens use `export_ue.py --armature-export-name Armature` or rename the object.
* Animation export is not implemented yet (`bake_anim = False`).

## 12. Source repository layout (`.blend` sources, separate LFS repo)

One `.blend` per asset by default (clean file locking and history in LFS; the plan keeps sources in their own LFS repo).
The folder path **is** the content path, so nobody maintains a mapping:

```
dink-blender-sources/            (Git + LFS: *.blend, *.png, *.exr, *.psd, *.kra, *.glb)
  Props/<dink_path>/SM_Barrel_01.blend             -> /Game/Dink/Props/<dink_path>/SM_Barrel_01
  Foliage/<dink_path>/SM_Tree_Oak_01.blend         -> /Game/Dink/Foliage/...
  Kits/<KitName>/KIT_<KitName>_Walls.blend         several kit pieces of one family may share a file (each collection exports alone)
  Buildings/<dink_path>/SM_House_Stonebrook_01.blend
  Items/SM_Sword_Iron_01.blend                     weapons, held items
  Characters/<Name>/SK_<Name>.blend                mesh + skeleton; Rig/ for the control rig, animations later
  Creatures/<Name>/SK_<Name>.blend
  Shared/Rigs/SK_Dink_Humanoid.blend               reference armature all humanoids start from
  Shared/Materials/materials.blend                 library of MI_ placeholders
  Textures/<dink_path>/                            painted/baked sources (.kra, .psd) and outputs T_*.png
  Generated/<tool>/<id>/                           raw AI-generator output, kept untouched for the ledger
  Ledger/asset_ledger.csv                          one row per generated/third-party asset: tool, model, licence, redistribution proof
  out/                                             ignored: export output
```

* `dink_path` in the collection equals the sub-folder under the class folder, so `Props/Tavern/SM_Barrel_01.blend` has `dink_path = Tavern`.
* The tools live in the main repo (`tools/blender/`); the sources repo calls them by path (e.g. `$DINK_TOOLS`). Export output goes to
  `out/export/Game/Dink/...`, which mirrors the Unreal Content folder, plus `manifest.json`.
* Never edit an exported file. The `.blend` is the only source of truth.
* Generated meshes enter through `import_generated.py` into `Props/...`, with `--source` filled in, and get a ledger row the same day (plan section 9 rule).

## 13. Workflow in one paragraph

Import (`import_generated.py`) or model, put it in a collection with `dink_class`, run `fix.py --all-safe --rename`,
`make_lods.py --lods --collision`, `validate.py` until it exits 0, then `export_ue.py`. Commands and the agent checklist are in `README.md`.
